Status: specification independently reviewed and accepted; the pinned fixture,

The narrow native-attendance gate is enabled. The focused test, targeted
queries, full Duvet trace, formatting, and strict Clippy pass. Full local CI

`69b862b4775eb420880da2ec6a8d332b51936f809f550d84d715e08c7a77008e`
(Verus 2,047/3,183/1,371, zero errors). Hosted Linux/Pages checks remain
pending.

## Goal and scope

Establish one end-to-end public-reader compatibility result for an official
Duplicity 3.0.7 archive encrypted to a version-4 RSA-2048 recipient key. The
checked-in official encrypted corpus currently exercises cv25519 recipient
recovery, while the adapter's RSA wire-policy tests do not establish successful
RSA decryption. This case closes that specific evidence gap under
[PARSE-ENV-008](parsing-requirements.md#parse-env-008).

The acceptance is limited to one completed Full manifest and its one required
encrypted data volume, using the AES payload cipher recorded in fixture
provenance. It exercises the real public `Catalog::read_snapshot_with_crypto`
composition and one selected snapshot date. It makes no Verus claim about RSA,
cryptographic primitives, or complete reader control flow.

## Fixture and source requirements

1. The fixture MUST be a separately checked-in package under
   `tests/fixtures/duplicity-3.0.7/` generated by official Duplicity 3.0.7 and
   GnuPG from a deterministic source tree and a test-only v4 RSA-2048 key.
   Provenance MUST preserve the exact tool versions, normalized producer argv,
   source recipe, recipient fingerprint, fixture object names, byte lengths,
   and SHA-256 hashes. The protected secret-key export and its test passphrase
   MUST be recorded as public test credentials, not supplied from the
   developer's keyring. Provenance MUST record the secret export's protection
   usage and S2K profile, and confirm that this specific export fits the
   supported import forms enumerated by
   [PARSE-ENV-009](parsing-requirements.md#parse-env-009). This is fixture
   qualification only; it does not expand this acceptance to general ENV-009
   behavior.
2. The producer MUST emit a single Full backup with exactly one required data
   volume. The package MUST contain the Full manifest and that volume only;
   provenance MUST define the synthetic `ObjectSource` identity policy
   explicitly: each object has version ID `rsa2048-fixture-v1` and an ETag
   equal to the lowercase hexadecimal SHA-256 of its exact stored bytes. The
   test MUST assert exact catalog object keys, parsed kind/interval/ordinal,
   envelope, stored size, version ID, and ETag-to-SHA-256 correspondence for
   both objects. The read MUST use those same catalog identities. The test MUST
   assert the exact ordered two-key source-open log: Full manifest followed by
   Full volume 1.
3. Independent fixture inspection MUST establish that the recipient is a v4
   RSA key with a 2048-bit modulus, the selected wrapper is PKESKv3 using RSA,
   and the payload uses AES-256 (OpenPGP symmetric algorithm ID 9). Record that
   exact algorithm ID in provenance; this acceptance covers only this one
   cipher from PARSE-ENV-008. The PKESK recipient key ID MUST be recorded and
   resolved to the matching fingerprint of the exported RSA-2048
   encryption-capable primary key or subkey; provenance MUST identify which
   component it is and record its OpenPGP public-key algorithm ID. This
   inspection is fixture provenance, not a runtime GnuPG dependency or proof
   of the project's crypto primitives.
4. Provenance MUST include an independent source-content oracle for the
   selected snapshot, sufficient to compare raw component paths, entry kinds,
   modes, timestamps, file sizes and SHA-256 content digests, and symlink
   targets where present. It MUST also record the Duplicity source manifest
   interval and the exact target timestamp used by the test.
5. Tests MUST load the checked-in artifacts and MUST NOT invoke Duplicity,
   GnuPG, or another crypto executable at runtime. No live S3 access is
   required.

## Normative acceptance requirements

### 1. Metadata-only discovery

`Catalog::discover` MUST identify the single completed Full manifest and
required FullVolume 1 without opening either object's body. The catalog MUST
contain exactly those two fixture objects, and the source-open log MUST remain
empty after discovery.

### 2. RSA-encrypted snapshot recovery

Using a `CryptoReadContext` containing only the checked-in RSA secret export
and its test passphrase, with no message passwords, signer exports, or
permitted signers, `Catalog::read_snapshot_with_crypto` MUST return the
selected Full snapshot. The source MUST be the same immutable source instance
used for discovery. The ordered open log MUST contain exactly the manifest key
and then the required volume key, each once.

The returned snapshot MUST match the independent source-content oracle for
every selected entry: raw component sequence, entry type, `mode() & 0o777`,
mtime seconds and nanoseconds, regular-file length and SHA-256 content digest,
and symlink target bytes. Entry iteration MUST match oracle order by raw path
components as required by
[PARSE-STATE-003](parsing-requirements.md#parse-state-003). Any official-oracle
exclusion MUST be explicitly recorded in the fixture provenance and acceptance
assertions; no unrecorded field exclusion is permitted.

The result MUST contain exactly two authentication records, for the Full
manifest and its required data volume. Both MUST report integrity-only
`OpenPgpIntegrity` evidence with no signer fingerprint. The call MUST return
the snapshot and evidence receipt only after both required objects have
completed their configured integrity checks.

### 3. Credential isolation

The test MUST assert that the message-password, signer-export, and
permitted-signer inputs are empty. It MUST use the fixture's exported RSA
secret key, not an ambient GnuPG keyring or machine credential. Test output,
errors, and logs MUST NOT include secret-key bytes or passphrases.

## Requirement and assurance mapping

The new test MUST link to PARSE-ENV-008 for the enumerated RSA recipient
capability and PARSE-STATE-003 only for the explicitly asserted snapshot entry
ordering. It MUST NOT claim AES-128/192 coverage, RSA signing compatibility,
other RSA modulus sizes, or the whole algorithm matrix in PARSE-ENV-008.

The test SHOULD remain registered under the existing OpenPGP reader edge-test
ledger. To enforce Duvet attendance without implying formal crypto proof, the
implementation SHOULD add a narrow gated native milestone, for example
`openpgp-rsa-pkesk-compatibility`, listing this exact test and the public reader
composition implementation. It MUST use `proof_required = false` and state
that it enforces native Duvet/test attendance only. Enable that gate only
after independent implementation review accepts the test and mapping. No
Verus model of RSA or whole-reader behavior is required or claimed.

## Explicit exclusions

This acceptance does not establish RSA signing, RSA keys larger than 2048
bits, AES variants other than the one recorded in this fixture, official
signing-subkey compatibility, certificate expiry/revocation policy, resistance
to RSA timing/Marvin attacks, cryptographic primitive correctness, other
Duplicity versions, multiple-volume RSA chains, incremental RSA chains,
filesystem publication, live S3 behavior, or complete reader/controller
refinement. The trusted OpenPGP dependency and crypto adapter remain outside
formal proof.
