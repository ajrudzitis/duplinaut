## Goal and scope

Verify the positive companion branch to the unsupported-only digest case: a
volume remains readable when its manifest declares an unknown digest algorithm
alongside a supported digest that validates the original stored bytes. The
reader must not reject the object solely because an unsupported declaration is
also present. This is one in-memory mutation of the official Duplicity 3.0.7
plain fixture; no fixture file or producer output is changed.

## Fixture mutation

Start from the exact twelve objects in
`tests/fixtures/duplicity-3.0.7/plain/`. In the body of

```text
backup/duplicity-inc.20231114T221320Z.to.20231115T221320Z.manifest
```

locate the Volume 1 `Hash SHA1 <hex>` declaration. Insert immediately after it
one `Hash SHA2 <hex>` declaration using the same 40 hexadecimal digits as the
SHA1 declaration. Preserve the original SHA1 declaration and all other
manifest content. The inserted unsupported declaration is syntactically
valid but ignored for integrity calculation. Preserve the baseline fixture's
known-supported SHA1 declaration and associated stored bytes for

```text
backup/duplicity-inc.20231114T221320Z.to.20231115T221320Z.vol1.difftar.gz
```

Update only the changed manifest object's stored size and test-local identity
metadata (recomputed ETag and distinct synthetic version ID). The remaining
eleven objects, including all data payloads and identities, stay unchanged.
Assert the exact insertion and unchanged original digest before discovery.
This synthetic manifest is not an official producer output or an S3 identity
claim.

## Required public observations

1. Public `Catalog::discover` MUST perform zero source opens and expose the
   same three name-derived Full/Incremental descriptors as the fixture. Derive
   the Full anchor from `Catalog::manifests()`.
2. Public `Catalog::read_snapshot` at `Timestamp(1700172800)` MUST succeed.
   Compare the resulting final snapshot with the unchanged plain entries in
   `tests/fixtures/duplicity-3.0.7/expected.json`: raw component-byte paths,
   entry kinds, `mode() & 0o777`, exact regular-file and directory mtimes in
   seconds/nanoseconds, regular-file sizes and SHA-256 values, and symlink
   target bytes. `SnapshotState::entries()` MUST enumerate paths in the same
   order as the oracle's raw component sequences, compared lexicographically
   as unsigned bytes with component boundaries significant and proper
   component-sequence prefixes ordered first. Omit symlink mtime per the
   producer's recorded comparison exclusion.
3. Require exactly the nine required chain objects to be opened, once each:
   the Full, first-Incremental, and final-Incremental manifests; Full volumes
   1/2/3; first-Incremental volumes 1/2; and final-Incremental volume 1. No
   signatures archives or unrelated objects may be opened.

The snapshot comparison is a regression oracle for unchanged official data;
it does not claim that the mutated manifest itself was generated by official
duplicity.

## Requirements and verification

1. MUST NOT reject a selected volume as unsupported-integrity solely because
   an unknown digest declaration accompanies a supported declaration. The
   final public read MUST succeed. Link this positive branch to
   `PARSE-ENV-006`.
2. MUST preserve the official supported SHA1 declaration and its original
   volume bytes as the positive fixture precondition. This case relies on the
   existing `PARSE-ENV-005` digest-validation evidence; it does not claim to
   re-prove digest enforcement.
3. MUST reconstruct the final snapshot and avoid opening irrelevant signature
   archives or objects.
4. MUST expose `SnapshotState::entries()` in bytewise lexicographic order of
   backup-relative path components, preserving component boundaries and
   ordering a proper component-sequence prefix before its extension. The test
   checks the final snapshot's observed order against the raw-component oracle
   and links this assertion to `PARSE-STATE-003`.

Add a focused integration test in `crates/core/tests/reader.rs`, annotated
with Duvet `PARSE-ENV-006` and `PARSE-STATE-003`. Do not add
`ASSURE-TEST-001`: the manifest is test-mutated and the test is scoped to
digest-policy behavior, not a claim that the mutated object is an official
producer output. No additional chain, S3, or filesystem-publication
requirement is needed for this slice.

Acceptance requires the focused test, targeted Duvet query and full trace,
focused/full core tests, formatting, strict Clippy, local `cargo xtask ci`,
independent implementation review, and hosted Linux assurance plus Duvet Pages
publication.

## Exclusions

This acceptance covers only an unknown `SHA2` declaration accompanying the
valid SHA1 digest for first-Incremental volume 1. It does not test unknown-only
declarations, malformed or conflicting digest syntax, other algorithms or
volume ordinals, alternate producer profiles, S3 identity races, encrypted
volumes, filesystem restoration, or complete reader/controller refinement.
